Informe Estratégico de Implementación: Ecosistema Digital de Lealtad y Soberanía de Datos para el Sector Hospitalario de San Cristóbal de Las Casas mediante el Marco Agéntico MoAI-ADK1. Análisis Situacional y Justificación Estratégica del Mercado1.1 La Brecha Digital en los Altos de Chiapas y el Imperativo de la SoberaníaLa economía de San Cristóbal de Las Casas, transformada de un centro comercial regional a un nodo turístico de relevancia internacional, enfrenta una paradoja crítica: posee una oferta física de clase mundial —hotelería boutique, gastronomía de autor y riqueza cultural— sustentada por una infraestructura digital precaria y dependiente. El análisis exhaustivo del documento "Auditoría Estratégica de Transformación Digital" revela una vulnerabilidad estructural en el tejido comercial de la región: la dependencia excesiva de intermediarios digitales (OTAs como Booking.com, Expedia y plataformas sociales como TripAdvisor).Esta intermediación no es benigna; genera una erosión sistemática de los márgenes de beneficio, que oscilan entre el 15% y el 25% por transacción, y, lo que es más grave, efectúa un "secuestro de datos" del cliente final. Los establecimientos locales, desde el Hotel Bo hasta restaurantes de tradición como Sol y Luna, operan a menudo sin acceso directo a la información de sus consumidores, impidiendo la construcción de relaciones de lealtad a largo plazo y limitando el Valor de Vida del Cliente (LTV). La oportunidad comercial no reside en la simple creación de páginas web informativas, mercado ya saturado, sino en la implementación de "infraestructuras de conversión directa" que devuelvan la soberanía de la marca y los ingresos al empresario local.1.2 La Necesidad de una Wallet Gamificada y Offline-FirstLa propuesta de desarrollar una aplicación tipo "Wallet" o cuponera digital responde directamente a las carencias identificadas en las verticales de hospitalidad y gastronomía.Identidad Fragmentada: Restaurantes como La Lupe, que sufren de una identidad digital dispersa entre múltiples dominios y conceptos confusos, requieren una plataforma unificada que centralice la experiencia del usuario y clarifique la narrativa de marca "Maíz y Agave" frente a ofertas discordantes.Experiencia vs. Transacción: Establecimientos de "Lujo Experiencial" como Casa del Alma necesitan herramientas que vayan más allá de la transacción simple. Una app gamificada permite extender la narrativa de bienestar y exclusividad, transformando una visita ocasional en una progresión de estatus (bronce, plata, oro) que desbloquea experiencias únicas, no solo descuentos.Resiliencia Tecnológica: La infraestructura de internet en Chiapas es inestable. Una aplicación que dependa de una conexión constante al servidor para validar una visita fallará en el momento crítico del pago. Por tanto, la arquitectura debe ser Offline-First (Primero Fuera de Línea), permitiendo que el escaneo del código QR y el registro de la transacción ocurran localmente y se sincronicen posteriormente, garantizando la continuidad operativa sin fricción para el turista o el mesero.1.3 El Paradigma del Desarrollo: Vibecoding Estructurado con MoAI-ADKPara ejecutar este proyecto con la velocidad requerida por un mercado dinámico y la robustez necesaria para transacciones financieras, adoptamos una metodología híbrida. Fusionamos el "Vibecoding" —una aproximación fluida e intuitiva a la codificación asistida por IA— con el rigor de la ingeniería de software impuesto por MoAI-ADK (Agentic Development Kit).El Vibecoding puro, aunque rápido, tiende a generar código frágil y difícil de mantener ("spaghetti code") cuando el contexto del proyecto crece. MoAI-ADK mitiga este riesgo introduciendo una jerarquía de agentes autónomos especializados (como manager-spec, expert-backend, manager-quality) que operan dentro del IDE Windsurf. Este marco asegura que cada línea de código generada por la "vibra" creativa esté respaldada por especificaciones técnicas rigurosas (formato EARS), pruebas automatizadas (TDD) y documentación sincronizada en tiempo real.2. Arquitectura Técnica del MVP: Resiliencia y Seguridad2.1 Diseño del Sistema Offline-First (PWA)La solución se concibe como una Progressive Web Application (PWA) dual, sirviendo dos interfaces distintas (Cliente y Personal) desde un mismo núcleo tecnológico, optimizado para Next.js 14.Componentes Clave de la Arquitectura:CapaTecnologíaJustificación TécnicaFrontendNext.js 14 (App Router)Permite renderizado híbrido. Las páginas de marketing son estáticas (SSG) para SEO, mientras que el dashboard de usuario es dinámico y renderizado en el cliente (CSR) para interactividad instantánea.Motor de SincronizaciónTanStack Query + IndexedDB (Dexie.js)Gestiona el estado del servidor en el cliente. Cuando no hay red, las mutaciones (ej. registrar visita) se persisten en IndexedDB y se reintentan automáticamente al recuperar conexión, crucial para San Cristóbal.Backend (BaaS)SupabaseProvee base de datos PostgreSQL, autenticación y políticas de seguridad a nivel de fila (RLS). Elimina la necesidad de mantener servidores dedicados, reduciendo costos operativos para los negocios locales.IdentidadSupabase AuthManejo seguro de roles (Administrador, Empleado, Cliente) integrado directamente con las políticas de acceso a datos.2.2 Protocolo de Seguridad: Código QR Dinámico Firmado (JWT)Uno de los riesgos más altos en sistemas de lealtad basados en QR es el fraude por "Replay Attack" (ataque de repetición), donde un usuario toma una captura de pantalla de su código y la comparte con amigos, o la usa múltiples veces. Para mitigar esto, implementamos un protocolo de Tokenización Dinámica.El flujo de seguridad es el siguiente:Generación (App Cliente): El dispositivo del cliente genera un nuevo código QR cada 30 segundos. Este QR no contiene simplemente el ID del usuario, sino un JSON Web Token (JWT) firmado criptográficamente.Payload del JWT: { "sub": "user_uuid", "iat": timestamp_actual, "nonce": aleatorio_unico, "exp": timestamp + 60s }.Firma: El JWT se firma utilizando un secreto compartido (o clave privada en un esquema asimétrico) que solo el backend y la app de validación conocen/pueden verificar.Verificación (App Empleado):El escáner del empleado lee el QR.Verifica la firma digital para asegurar que no fue falsificado.Verifica que el exp (tiempo de expiración) no haya pasado. Si el QR tiene más de 60 segundos de antigüedad, se rechaza, invalidando las capturas de pantalla antiguas.Verifica el nonce contra una caché local o remota para asegurar que ese código específico no se haya usado ya.2.3 Modelo de Datos Relacional (Esquema PostgreSQL)El diseño de la base de datos debe reflejar la jerarquía de roles y la integridad de las transacciones financieras (puntos).Tablas Principales:profiles (Perfiles): Extensión de la tabla de autenticación. Almacena datos públicos del usuario, su rol (admin, staff, customer), su saldo actual de puntos y su nivel de lealtad (tier).establishments (Establecimientos): Datos de los restaurantes participantes (Sol y Luna, La Lupe, etc.). Permite que la app escale a un modelo multi-inquilino si se desea crear una red de lealtad de la ciudad.transactions (Transacciones): Libro mayor inmutable. Cada fila representa un evento de ganar o gastar puntos.Columnas: id, user_id, staff_id, establishment_id, amount_mxn, points_change, transaction_type (EARN/REDEEM), timestamp, sync_id (para rastreo offline).Seguridad (RLS): Los clientes solo pueden leer sus propias transacciones (SELECT using auth.uid() = user_id). Los empleados pueden crear transacciones (INSERT) pero no modificarlas ni borrarlas.rewards (Recompensas): Catálogo de beneficios canjeables. Incluye lógica de bloqueo por nivel (ej. "Solo disponible para nivel Oro").3. Prioridad en reservas (solucionando el dolor de Sol y Luna). El usuario se convierte en promotor de la marca.3.2 Mecánicas de RetenciónEfecto de Gradiente de Meta: La interfaz mostrará barras de progreso visuales indicando "Faltan $200 para subir a nivel Plata". Los usuarios tienden a acelerar su consumo a medida que se acercan a una meta visible.Bonificaciones Temporales: Para combatir las temporadas bajas de turismo en San Cristóbal, el administrador podrá activar "Horas Felices de Puntos" (ej. doble puntos los martes lluviosos), incentivando la visita en momentos de baja demanda.4. Especificación de Requerimientos (Formato EARS)Para garantizar la calidad y reducir la ambigüedad, utilizamos la notación EARS (Easy Approach to Requirements Syntax). Esta estructura es fundamental para que los agentes de IA comprendan la lógica condicional compleja.5.1 Módulo: Gestión de Identidad y Roles[Ubiquitous - Ubicuo] El Sistema debe restringir el acceso a las vistas administrativas exclusivamente a usuarios con el rol de 'admin' o 'staff' validado por Supabase Auth.**** Cuando un nuevo usuario se registra exitosamente, el Sistema debe crear automáticamente un registro en la tabla profiles con el nivel inicial 'Explorador' y un saldo de 0 puntos.**** Mientras el usuario tenga una sesión activa como 'staff', la Aplicación debe mantener la pantalla del dispositivo despierta (wake lock) para facilitar el escaneo continuo.5.2 Módulo: Billetera y Generación de QR (Cliente)[Ubiquitous] La Aplicación del Cliente debe generar códigos QR que contengan un payload JWT firmado criptográficamente.**** Mientras el código QR se muestra en pantalla, la Aplicación debe regenerar el payload y actualizar el gráfico QR cada 30 segundos para prevenir ataques de repetición.**** Cuando el dispositivo detecta pérdida de conectividad a internet, la Aplicación debe cambiar al modo 'Offline-Generation', utilizando el último token de sesión válido almacenado en caché segura.5.3 Módulo: Escáner y Procesamiento de Transacciones (Empleado)**** Cuando el Empleado escanea un código QR válido, el Sistema debe mostrar inmediatamente un modal con el nombre del cliente y su nivel de lealtad actual.**** Si el código QR escaneado tiene una marca de tiempo (timestamp) con una antigüedad mayor a 60 segundos, entonces el Sistema debe rechazar la transacción y mostrar un mensaje de error "Código Expirado".**** Cuando se confirma una transacción de pago, el Sistema debe calcular los puntos ganados aplicando el multiplicador correspondiente al nivel del usuario (1x, 1.2x, 1.5x) y registrar la operación en la tabla transactions.5.4 Módulo: Sincronización y Resiliencia (Core)**** Mientras la aplicación se encuentre en estado 'disconnected' (sin internet), el Sistema debe almacenar todas las transacciones de acumulación de puntos en una cola local persistente (IndexedDB).**** Cuando la conectividad de red se restaura, el Sistema debe iniciar automáticamente un proceso en segundo plano para enviar las transacciones en cola al servidor Supabase.**** Si ocurre un conflicto de sincronización (ej. saldo insuficiente al procesar offline), entonces el Sistema debe marcar la transacción como 'conflicto' y notificar al administrador para resolución manual.6.
